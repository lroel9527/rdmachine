# 文件复制粘贴

3.3.0 起有，4.0.0 补齐断线续传、扩展属性等，4.1.0 加了压缩。做法依据 2026-11-14 在一台 Mac mini（macOS 27.2，Apple 芯片）上做的实验，测试程序没有放进仓库。

## 做什么

在一台 Mac 的访达里复制（⌘C）文件，到另一台的访达里粘贴（⌘V），两个方向都能用，全屏和窗口模式都能用。要比 `scp` 用起来更顺手。

规则和文本、图片一样：**文件只在对方真正粘贴时才传**。rdmachine 在后台时，宿主机上的复制不会引起任何上传。

没有的：拖放（全屏是最常用的方式，那时看不到本机的访达，有复制粘贴就够了）、SFTP 式的传输窗口（本质上还是在两边找路径）。见[决定](decisions.md)的“文件复制粘贴”。

## 苹果的屏幕共享怎么做

在本机系统里查了它的程序引用了哪些函数（`nm -u`、`strings`）：

- 复制粘贴：被控端的辅助进程 `ScreensharingAgent.bundle/Contents/Support/SSPasteboardHelper` 用 Carbon 的 Pasteboard 接口：`PasteboardSetPromiseKeeper`、`PasteboardPutItemFlavor`（`com.apple.pasteboard.promised-file-url`、`promised-file-content-type`）、`PasteboardResolvePromises`，日志字样有 “added URL promise”“%s is wanted for the paste”。
- 拖放：`AppleVNCServer.bundle/Contents/Support/SSDragHelper.app` 用私有的 CoreDrag 接口（`CoreDragCreateWithPasteboardRef`、`CoreDragStartDragging`），在被控端发起真正的拖动。
- 会话期间关掉通用剪贴板（字样 “disable universal clipboard”；苹果文档也说屏幕共享期间通用剪贴板不可用）。

## 实验结论

| 试了什么 | 结果 |
| --- | --- |
| 剪贴板上只放 Carbon 文件承诺（`promised-file-url` + `promised-file-content-type`） | 访达的“粘贴”是灰的，没有人来取 |
| 只放 `NSFilePromiseProvider` | 同样是灰的 |
| 放一个延迟提供的 `public.file-url` | 1 毫秒内就被读走：读的是系统的通用剪贴板（pboard 日志 “Remote pasteboard fetching local data”），我们自己的服务端也会读（`Read()` 里的 `canReadObjectForClasses`） |
| 加 `prepareForNewContents(with: .currentHostOnly)`（只限本机）和 `org.nspasteboard.TransientType` | 没有人提前读了 |
| 切到访达、按 ⌘A、⌘1 | 访达不读 |
| 按 ⌘V，或者打开“编辑”菜单 | 访达立刻来要文件地址，在主线程上等着；模拟 10 秒传输，访达就卡 10 秒，之后粘贴成功 |
| 第一次来要时不给 | 访达不会再来要，⌘V 报“一个或多个项目已删除或不再可用” |
| 文件地址指向 File Provider 域里的占位文件（50 MB，0 个磁盘块，`dataless`） | ⌘V 立刻返回；访达弹出自己的“拷贝”进度窗口，期间一直响应（辅助功能查询 0.15 秒内回答）；扩展的 `fetchContents` 用了 20 秒，文件完整到达 |

两点修正 2.2.0 当时的结论：

- “访达一读文件路径就开始传”，主要读的其实是通用剪贴板和我们自己的服务端。访达只在粘贴或打开“编辑”菜单时才读。
- “访达的粘贴不接受文件承诺”是对的：访达粘贴只认真实的文件地址。所以要“粘贴时才传”，得让地址先指向一个还没有内容的文件，这就是 File Provider。

File Provider 的条件，都已验证：

- 自签证书（`rdmachine Local Signing`）就可以，不需要开发者账号；只用命令行工具打包，不需要 Xcode。扩展只要沙盒权限，App 放在“应用程序”里，用 `lsregister` 和 `pluginkit` 登记。
- 隐藏的域（`hidden`）永远不会被启用，只能用可见的域，访达侧边栏的“位置”里会多一项（“RDMachine”）。
- 域刚建好时是停用的，用户要在“系统设置 → 通用 → 登录项与扩展”里打开一次。

## 怎么工作

### 流程

1. **复制的一方**：和别的剪贴板内容一样，只宣布，不传内容。复制的是文件时，宣布每个文件的名字、大小、类型和修改时间（文件夹带上里面的结构）。
2. **粘贴的一方**：
   - 在自己的 File Provider 域里为这些文件建占位项（只有元数据）；
   - 往剪贴板上放延迟提供的 `public.file-url`，每个文件一项，指向这些占位项；整个承诺都用 `currentHostOnly`，加上我们自己读剪贴板时会跳过的标记。
3. **⌘V**：访达拿到地址，立刻开始拷贝，可以在它的窗口里取消。系统回调扩展的 `fetchContents`，扩展经主程序向对方要内容，写进临时文件交给系统。
4. **不传的情况**：会话结束（90 秒内没回来，见下）、用户在访达里取消，都取消传输，占位项作废。对方又复制了别的不打断正在取的（见下）。

两边都有扩展：服务端和客户端各带一个（远程 → 本机时，粘贴的一方是客户端）。扩展是沙盒进程，和主程序之间用 XPC 通信（`NSFileProviderServicing`），主程序负责网络。

### 代码

- `core/`：`file_transfer.h`（清单、流、收发；平台无关，POSIX 文件），接在 `ClipboardSync` 里，消息见[协议](protocol.md)的“文件（剪贴板版本 4）”。
- `fileprovider/files_extension.m`：扩展，复制放在内存里；文件夹的内容要用时才问（list），文件要用时才取（fetch）。和主程序之间的 XPC 协议在 `fileprovider/rdm_files_xpc.h`：主程序连扩展在域根目录上提供的服务，扩展在同一条连接上回调主程序；取到的文件以文件句柄交过去，扩展克隆进系统的临时目录。
- `session/src/file_target_mac.mm`：主程序这一侧，进程里的会话共用一个域和一条连接。
- `session/src/system_clipboard_mac.mm`：复制时读出文件路径；粘贴的一方写延迟提供的文件地址。
- 打包：`package.sh` 把 `RDMachine Files.appex`（标识是应用的标识加 `.files`）放进两个应用，只给沙盒权限，单独签名。

### 占位项

- 占位文件要等它的文件夹被展开才会出现在磁盘上（在那之前系统让它等父目录，fileproviderctl 里是 `⧗parentCreation`）。发布后调用 `requestDownloadForItemWithIdentifier`（macOS 13 起）请 File Provider 展开这份复制的文件夹，剪贴板给出文件地址前也列一次父目录。只靠列目录不行（3.3.2 的做法，3.4.2 改）：服务端作为 launchd 的 agent 运行时没有“完全磁盘访问”，系统（sandboxd 查 `kTCCServiceSystemPolicyAllFiles`，被拒）不替它展开 `~/Library/CloudStorage` 里的文件夹；粘贴时文件地址指向还不存在的文件，剪贴板服务建不了沙盒扩展（`Sandbox extension creation failed`），访达拿到空地址就粘贴文件名文本。从终端起的进程和用户打开的客户端没有这个限制，所以每次粘贴前在终端里 `ls` 看一眼的测试会把它掩盖。
- 条目标识带上时间（`c<秒数>-<序号>`，3.3.4）：系统按标识记条目，每次运行都从 `c1` 编号时，上一次运行留下的 `c1/0`（取失败、正在退避重试）顶替了这一次的，粘贴时根本不去取。
- 条目声明了可写（能力里有写、改名、删除，真改时拒绝）：只能读的条目会被打上锁定标记 `uchg`，访达连标记一起拷出来；这样粘出来的是普通文件。
- 扩展属性：访达标签之类的扩展属性跟着清单和流走，扩展把它们放在条目的 `extendedAttributes` 上，系统写到占位文件和拷出来的文件上；暂存文件也写上。系统自己的（沙盒、File Provider、压缩、SIP 的记账）不带，每项最多 16 KB，大的（比如大的资源分支）略过（4.0.0）。
- 可执行位跟着走（`UserExecutable`）；组和其他人的权限位不跟（见“已知的限制”）。

### 多份复制

复制的标识（announce id）是随机的、跨会话唯一（剪贴板版本 5，4.0.0）。复制的一方在进程里记住最近 32 份复制，按标识来取的都答；粘贴的一方新复制来了只把旧的那份从剪贴板上撤下，正在取的接着取。主程序（`file_target_mac.mm`）同时留着好几份复制，每份一个文件夹：不在剪贴板上、也没有在取的，闲一分钟再撤（访达可能还要取别的文件）；扩展同时放好几份，各自撤。

扩展记下每份复制是哪条连接发布的，那个程序退出、崩溃或重启（连接断了）就撤掉它的复制；不然侧边栏里会一直留着谁也取不了的复制（单独起的测试服务端结束后出现过）。

### 断线后接着传（4.0.0）

会话结束时，正在取的项记下写到哪里（`ResumeBook`，进程内），暂存的文件留着，扩展那边的请求也不报失败。主程序等同一个对端的下一个会话（客户端按服务端地址认，服务端认任何客户端），90 秒内回来就把还在等的项交给新会话再取，带上 `from` 从断开的地方接着发；没回来就报失败。重连后对方重新宣布剪贴板，那是新的一份，旧的那份照样取完。接管时（新会话先到、旧的后走）旧的一走，它手上的复制就交给新的。

### 传输

- **批量通道**（3.4.0，rdaccel 1.10）：文件数据走 rdaccel 的批量通道，排在视频之后，速度交给 rdaccel 的拥塞控制；发送方让通道里保持约 1 MB。分块、确认沿用剪贴板的做法。拿不到排队量（TCP、旧对端）时退回 `transfer_pacer.h` 按确认延迟猜排队的节奏：一个判断周期至少两个往返，排队的门槛是往返延迟的一半（至少 25 毫秒）（3.3.3；之前按局域网调，往返 200 毫秒的 VPN 上抖动本身一直触发降速，客户端发往服务端只有每秒 50 KB 左右）。
- **传文件时画面不卡**（rdaccel 1.10.1）：批量通道像 LEDBAT，在途数据只给带宽时延积再多四分之一，有排队时只给带宽时延积；它的排队门槛是几毫秒，和往返长短无关（给画面用的门槛是往返的四分之一），余量最多 10 毫秒。原来批量通道可以占满拥塞窗口（带宽时延积的两倍）的四分之三，瓶颈（客户端经 Tailscale 的上行）上一直站着排队，同方向的输入和画面的确认包在里面等：往返 190 毫秒的 VPN 上，客户端往服务端传时画面一卡一卡、操作不跟手。
- **QoS 标记**（rdaccel 1.10.1）：每个 UDP 包都标明类别：文件数据是“后台”（macOS 的 `NET_SERVICE_TYPE_BK`，DSCP CS1），画面、输入和其余的是“屏幕共享”（`NET_SERVICE_TYPE_RV`，DSCP CS4）。macOS 自己的队列和 Wi-Fi（WMM）按它排，客户端用 Wi-Fi 上网时文件包在空中会让路；VPN 隧道一般不把标记抄到外层，路由器和运营商大多不看，所以这只是补充，主要还是靠批量通道自己不留排队。TCP 画面连接不打标记。
- **乱序**（3.4.1）：rdaccel 从迟到的包学一个乱序窗口，不把乱序当成丢包。
- **UDP 等待**（3.3.5）：等 UDP 的时间随登录用时放宽（登录用时的两倍，4 到 15 秒）；500 毫秒往返下 UDP 握手连同登录要 4 到 5 秒，原来正卡在客户端等 4 秒的门槛上。
- 发送端每 5 秒记一行速率、在途字节和基准延迟（`files: sending at ...`）。

### 压缩（4.1.0）

文件内容用 Zstandard 1 级压着传（协议见[协议](protocol.md)里的 zdata），128 KB 一块单独压，压不动就原样发。要两边都 4.1.0。

### 部分内容（3.4.0）

扩展实现了 `NSFileProviderPartialContentFetching`（macOS 12.3 起）。一个文件开始收，主程序就把暂存文件的句柄交给扩展（`fileGrowing`），之后按收到的字节回报；系统要某个范围时，已到的部分覆盖了它，扩展就把暂存文件此刻的克隆连同从对齐起点到已到末尾的整段交出去。访达拷贝时系统只调用整个文件的 `fetch`，从不按范围取（论坛上也有人报告按范围取会让访达拷贝超时），所以部分内容只在别的程序直接读文件时起作用（比如 `cat` 一个占位文件）。

### 进度

- 系统给 RDMachine 位置里的源文件发布真实的“下载中”进度（3.3.3 起每 256 KB 报一次，大小一开始就给系统），访达在占位文件上画会动的圆圈，和 iCloud 一样。圆圈只出现在粘贴那台 Mac 上访达侧边栏“RDMachine”位置里的占位文件上，不在复制那台 Mac 的原文件上。访达侧边栏“RDMachine”那一行可能也会出现系统画的进度饼图（系统给这个位置的根目录发布了“下载中”的进度，访达里有画这种进度的代码），没有亲眼确认过。
- 访达的拷贝窗口和粘贴目标在下载期间不动（见“已知的限制”），所以粘贴的一方在菜单栏图标上自己显示（4.0.0）：有文件在路上时，图标变成一个进度圆环（模板图，深浅色菜单栏都对），按收到的字节填满，传完变回原样；鼠标停在上面或点开菜单能看到“正在接收“报告.pdf” 23.4 / 60 MB · 2.3 MB/秒 · 约 16 秒”。只算访达真的在取的项；文件夹的总量等它的目录树到了才知道，在那之前圆环是一小段弧。服务端用原来的菜单栏图标；客户端有自己的菜单栏图标，平时显示连着几台电脑，菜单里列出各个连接（点一下把窗口调到前面）、电脑列表、新建连接、退出。数据来自主程序本来就交给扩展的进度（`file_target_mac.mm`，`CurrentFileReceive`），扩展和协议不参与。

### 第一次使用

RDMachine 在系统设置里没打开时，复制的文件只能粘贴出文件名。安装包以登录用户的身份运行 `--register-files` 注册域（3.3.1；域不存在时设置里的开关拨不动），装完开关就能拨。真的粘贴了这些文件名时（不是复制时），粘贴那台 Mac 上弹一个提示，说明在哪里打开，按钮“打开设置”直接打开“登录项与扩展”；十分钟内最多一次（4.0.0）。提示用 `CFUserNotification`，服务端作为 agent 也能弹，用户在远程画面里看得到。

自动打开开关做不到：`NSFileProviderDomainTestingModeAlwaysEnabled` 需要 `com.apple.developer.fileprovider.testing-mode` 权限，带它的自签程序一启动就被系统杀掉（试过），要开发者账号和描述文件，而且苹果说那是测试用的。

## 怎么验证

- **单元测试**：core 的流、路径、遍历、整棵文件夹、取消、老版本。
- **同一台 Mac 上的测试应用**（两端在同一个进程里，网络以外都是真的，3.3.0）：在访达里粘贴一个 30 MB 文件夹（子文件夹、中文名、符号链接）和一个 5 MB 文件：⌘V 后访达立刻开始，几秒内全部到达，校验和一致，没有锁定标记。测之前不要在终端里 `ls` 占位文件夹，否则会掩盖展开的问题（见“占位项”）。真实连接上的端到端测试是 `FilesE2E`，要录屏权限。
- **远链路**（3.3.5，本机模拟）：一个用户态延迟代理夹在 `rdmachine-connect --copy-files` 和单独起的服务端（`--standalone --headless --port=4200`）之间，每个方向 250 毫秒加 0 到 50 毫秒抖动（往返约 500 毫秒），客户端上行限 20 Mbps。60 MB 文件在访达里粘贴：画面走 TCP 时 29 秒（约 2.4 MB/s，跑满限速），走 UDP 时 43 秒（约 1.4 MB/s）；校验和一致，访达一直响应，系统的下载进度和收到的字节一致。代理让 UDP 包各自独立延迟（相差几十毫秒的大幅乱序）时，UDP 只剩约 0.5 MB/s；3.4.1 的乱序修复后，模拟链路上 200 毫秒往返、10 Mbps 加 50 毫秒乱序仍有 8 Mbps（修复前 2.9）。
- **画面和输入**（rdaccel 1.10.1，模拟）：往返 190 毫秒、抖动 3 毫秒，传输期间输入单程中位数 97 毫秒（路径 95，原来 104），最坏 124 毫秒（原来 150）。链路 10 Mbps、单程 20 毫秒：传输期间输入单程从 35 毫秒降到 26–29 毫秒，文件速度从 9.6 降到约 8.2 Mbps。
- **进度**（4.0.0，本机，20 Mbps，60 MB，`cp` 一个占位文件，和访达一样整个取）：进度 0% 到 96% 逐秒变化。用 `cat` 读占位文件时系统按范围取，进度一闪一闪、一直是 0，那不是访达的路径。3.4.0 订阅源文件的进度看到 0%→91.5% 逐秒变化。
- **压缩**（4.1.0，这台 Mac，128 KB 一块，和 `scp -C` 用的 zlib 6 级整流对比）：

| 样本 | 大小 | zstd 1 级 | zlib 6 级 |
| --- | --- | --- | --- |
| 系统词表（文本） | 2.5 MB | 34.5%，549 MB/s | 30.2%，35 MB/s |
| 本仓库源码 tar | 2.0 MB | 51.8%，844 MB/s | 49.0%，74 MB/s |
| rdmachine-server 可执行文件 | 3.7 MB | 40.9%，868 MB/s | 37.3%，56 MB/s |
| 系统桌面图片（HEIC） | 26.3 MB | 100%（原样发），12 GB/s 判定 | 100%，94 MB/s |

带宽是瓶颈的链路上（远的 VPN、慢的 Wi-Fi），代码和文本快两到三倍；局域网上压缩每秒几百 MB，不会拖慢。照片、视频、压缩包和以前一样。

两台 Mac 之间还没实测的：压缩、很多小文件、同名文件、断线后接着传。

## 已知的限制

- 组和其他人的权限位会丢。File Provider 的条目只有 `fileSystemFlags`（只有自己的读、写、执行），系统按它设置占位文件和拷出来的文件的权限，我们交给系统的文件带着原来的权限也没用（0644 的文件粘出来是 0600）；没有别的接口。这是 File Provider 的限制。
- 访达的拷贝窗口和粘贴目标在下载期间不动：粘贴目标一直是 0 字节，访达等整个文件下载完才开始拷到目标，它的进度条量的是拷到目标的字节。用 File Provider 改不了：条目上的“下载中”属性在复制型扩展里被忽略，提前交出会继续写的文件不行，按范围取访达不用，给目标发布我们自己的进度访达不认（调研过苹果头文件、开发者论坛和访达程序里的字符串；也试过：订阅目标文件夹能收到访达为目标发布的“拷贝中”进度，我们为同一个地址发布的进度系统接受了，但访达不在目标图标上显示它）。只有真正搬到本机网络盘（WebDAV、NFS）上，访达自己的拷贝进度条才会跟着走，那是另一套做法，没有做。进度看菜单栏图标（见“进度”）。
- 用鼠标打开“编辑”菜单也会触发拷贝，比粘贴稍早。
- 登录窗口时不提供（那时没有用户会话）。
