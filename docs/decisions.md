# 第一阶段的决定

2026-11-06 和 lroel 一起定下，详细的备选方案和取舍见方案文档。

| 编号 | 决定 | 要点 |
| --- | --- | --- |
| 范围 | 第一阶段只做 Mac ↔ Mac，Intel 和 Apple Silicon 都支持 | Linux、Wayland、Windows、浏览器、移动端放到后续阶段 |
| D1 | 服务端：平台无关的 C++20 核心（`core/`）+ Objective-C++ 的 Mac 外壳 | 核心以后给 Linux 复用；认证解析代码配 fuzz |
| D2 | 客户端：原生 AppKit | 在 rdaccel 的 `examples/remote_mac` 基础上扩展；界面逻辑尽量放进核心 |
| D3 | 控制连接：TLS 1.3 + 首次确认证书指纹 | M0 支持系统账号密码和配对码；每次会话生成新的 rdaccel 密钥（[协议](protocol.md)） |
| D4 | TCP 4100 控制 + rdaccel UDP 画面，UDP 不通退回 rdaccel TCP | 换网络不断线以后靠 rdaccel 加连接 ID |
| D5 | M0 只控制已登录用户的物理桌面，M1 补登录窗口和锁屏 | 无显示器的虚拟屏放到 M2 实验 |
| 系统版本 | 最低 macOS 12.3 | 为了 2016 款 Intel MacBook Pro；rdaccel 从 1.0.1 起支持（[rdaccel#39](https://github.com/lroel9527/rdaccel/issues/39)），rdmachine 的子模块现在用 1.9.2 |
| 签名 | 暂无 Apple Developer 账号，M0 用本机证书签名自测 | 不做公证分发；用 `packaging/macos/create-signing-identity.sh` 建一张固定的自签证书，应用标识固定为 `org.rdmachine.server` / `org.rdmachine.client`，重新编译后权限不丢 |
| 桌面 | 客户端请求桌面，服务端建虚拟屏（2026-11-10） | D5 里“虚拟屏放到 M2”提前：HiDPI 只能在被控端解决，客户端缩放补不回来。客户端只说要什么（像素宽高 + 每点像素数），服务端用 `CGVirtualDisplay` 建一块同样规格的显示器，设为主屏，真实显示器镜像它，会话结束后恢复；没有显示器的 Mac 也因此能用。`CGVirtualDisplay` 没有公开头文件（BetterDisplay、DeskPad 等同样在用），按类名查找，系统没有或创建失败时退回共享真实显示器、客户端缩放。边界：规格和消息在 `core/`（`desktop.h`），建屏在 `session/`（`VirtualDesktop`）；rdaccel 只补了通用的两处（1.4.3：缩放系数从显示模式读、注入坐标跟随模式变化）。细节见[协议](protocol.md)的“请求桌面” |
| 文字模式 | 省流量：文字清晰、立刻到，客户端决定开不开（2026-11-10） | 目的是少花流量（按流量计费的链路），不是链路慢。优先级（lroel，2026-11-10）：先保障体验，再去省流量。体验要和普通模式一样（运动时整体走视频，不逐块决定；视频、滚动不降帧率），省在看不出来的地方：静止和打字的文字减色后用专门的编码，省 3–7 倍，滚动和拖窗省三到六成，影片基本不省。最初按“链路极慢、慢慢补”做，实际使用中占位色块停留太久，rdaccel 1.7 改成现在这样；链路真的慢时才退到“先保持旧内容、之后补上”。由客户端请求（View → Data Saver，记住选择；`session_request.text_mode` 和会话中途的消息）。边界：怎么编码全在 rdaccel（1.5 的 `text_mode`，1.6 起文字块用上下文编码，都是通用的），rdmachine 只有开关、消息（`core/` 的 `picture_mode.h`）和浮窗上的一行提示。默认关：正常链路上普通模式画质更好。文字模式下客户端默认请求 1 倍的桌面（2026-11-10）：2 倍桌面的像素是 4 倍，100 kbps 上一屏文字看全要 16 秒、1 倍约 10 秒；1 倍是被控端按 1 倍渲染的文字（不是 2 倍缩小的），客户端把每个像素原样放大成 2 × 2，字比 Retina 粗糙但边缘清楚。不想要可以在菜单里关（View → Data Saver at Standard Resolution）。这只是“请求桌面”的规格不同，协议没有新东西。细节见[协议](protocol.md)的“文字模式” |
| 剪贴板 | 复制时只宣布，粘贴时才取；文件不经过剪贴板（2026-11-10） | 一复制就发会把客户端上复制的一切（别处复制的密码等）送到被控端，所以只宣布格式，对方真正粘贴时才取那一种格式；连接前就在剪贴板里的不宣布。macOS 用 `NSPasteboardItem` 的延迟提供数据：系统在主线程上要数据，读的一方能等（试过 70 秒没超时），等待时我们转主线程的事件循环，窗口不卡。文件试过两种办法都不行：延迟提供文件路径时，访达在更新“粘贴”菜单时就会读，文件在粘贴之前就传了；文件承诺（`com.apple.pasteboard.promised-file-url`）访达的粘贴不接受。所以剪贴板只共享文件名，文件以后用明确的传输窗口（类似 SFTP / NoMachine 的 Transfer a file）。rdaccel 的应用消息排在画面前面，所以大图的节奏在 rdmachine 里控制（ack 变慢或服务端跳帧就慢下来），rdaccel 不改。旧客户端拿不到承诺，服务端照旧把文本推给它；客户端不推给旧服务端。细节见[协议](protocol.md)的“剪贴板” |
| 音频 | 第一阶段不做声音 | 不采集、不传输声音，不碰两端的音量（rdaccel 的屏幕采集不收声音：macOS 13 起显式设 `capturesAudio = NO`，12.x 没有这个属性）；测试也不涉及声音 |
| 服务端界面 | 菜单栏应用，不静默运行（2026-11-09） | 菜单栏图标显示状态、配对码、指纹、权限，提供断开和设置；调试数据浮窗在客户端（远程窗口右上角，点击穿透），服务端每秒发统计过去；`--headless` 给脚本和自动测试用 |
| rdaccel 改动 | 在 rdaccel 仓库里改，边界不混 | rdaccel 只放通用的采集、编码、传输和测量（例如 `rda_host_stats` 的丢包计数）；登录、会话、界面、设置、统计的展示都在 rdmachine。rdmachine 以 submodule 固定在 rdaccel 的版本上 |
| 下一步范围 | 先做登录窗口和锁屏下的连接，再做“保持登录”；不做自动重连（2026-11-11） | lroel 定的顺序：登录窗口（含从登录窗口登录进桌面）和锁屏最重要。自动重连不做：断开后用保存的密钥很快就能重新连上，够用。代价：断开时虚拟屏被拆掉，被控端的窗口挪回真实显示器，重连后再挪回来，布局可能变（程序都还在跑，不丢工作）。双因素、受信用户、用户管理、审批弹窗以后再说 |
| 登录窗口和锁屏 | 服务端拆成 LaunchDaemon + 每个图形会话一个 agent（2026-11-11） | daemon（root，开机运行）只做 TCP 4100、TLS、认证、密钥存储，以及决定把会话交给哪个 agent；它以 root 解析网络输入，所以保持精简。agent 是现在的服务端程序加 `--agent`，用 `LimitLoadToSessionType = Aqua, LoginWindow` 在登录窗口和每个用户会话里各跑一个，负责 rdaccel 采集、注入、虚拟屏，权限仍记在 `org.rdmachine.server` 名下。登录、锁屏、切换用户时控制连接留在 daemon 上、不用重新认证：daemon 让新会话的 agent 开新的 rdaccel 会话，把新端口和密钥发给客户端。安装改用 `.pkg`（`SMAppService` 要 macOS 13，最低版本是 12.3）。先实验再写：登录窗口里的 agent 能否拿到屏幕录制并采集、能否在登录窗口和锁屏的密码框里注入按键、登录窗口下能否建 `CGVirtualDisplay`（不能就共享真实显示器、客户端缩放）。限制：开着 FileVault 时重启后停在开机解锁界面，macOS 还没启动，连不上（重启前可用 `sudo fdesetup authrestart`）。2026-11-07 有一个没合并的草稿分支 `claude/m1-agent`（daemon 和 agent 之间的 Unix socket 协议），基于很早的代码，可以参考。实验结果：锁屏（2026-11-11）由用户会话里现在的服务端处理就行，锁屏时有画面、能输密码解锁（macOS 锁屏不启动登录窗口会话）；锁屏较久、显示器关掉后打不进字，rdaccel 1.9.2 注入前先声明用户活动、点亮显示器（2.2.3）。登录窗口：`tools/loginwindow-experiment/` 把已装的服务端作为登录窗口会话的 LaunchAgent 跑在 4200 端口，待测 |
| 从登录窗口登录 | 客户端代输密码，不保存（2026-11-11） | 密钥只证明客户端可信，没有 macOS 密码。连到登录窗口时，客户端弹框让用户输一次被控 Mac 的账号密码，经控制连接（TLS）交给 daemon；daemon 先用 PAM 核对，再让登录窗口里的 agent 填进登录窗口。密码只在内存里，用完清零，不写盘、不进日志。不做“钥匙串记住 macOS 密码”：客户端 Mac 被人拿到时，对方能一路登录进桌面。锁屏同理：用密钥连上后看到的是锁屏，解锁照样要密码 |
| 保持登录 | 钥匙串里的密钥，挑战签名（2026-11-11） | 用密码或配对码登录成功后，客户端问是否在这台 Mac 上保持登录。选是就生成 P-256 密钥对（有 Secure Enclave 的 Mac 放进去，不能导出；没有的，比如 2016 款 Intel MacBook Pro，放钥匙串：仅本机、解锁后可用、不同步 iCloud），在同一条已登录的连接上把公钥交给服务端，服务端记在这个 macOS 账号下。以后用密钥登录：客户端对“固定前缀 + 服务端证书指纹 + 服务端这次给的随机数 + 用户名”签名，服务端用记下的公钥核对；指纹已被客户端核对，所以签名拿到别处或录下重放都没用。每台客户端对每台服务端一把钥匙。服务端菜单列出已保持登录的设备，可以逐个撤销；客户端“退出登录”删掉私钥并通知服务端撤销；90 天没用自动失效；设置里可以整体关掉。密钥对应的账号不是当前登录的用户时拒绝（登录窗口除外）；失败照样计入按 IP 的限流。可选每次用钥匙都要 Touch ID 或密码，默认关。接受的风险：客户端 Mac 在解锁状态下被人拿到，对方能连上（同 SSH 钥匙）；改了服务端密码，钥匙不会失效，靠撤销解决 |
